## النتيجة

النسخة الحالية محرك Python محلي محدود، له اختبارات ومراجع وتتبع وتوقيت وفرضيات اختيارية وفحص إصلاح. أهم الفجوات إلى رؤية الملف هي الوكيل صاحب الحالة، واختيار الاختبار التالي من نتائج التنفيذ، وACDR، وقاعدة معرفة أخطاء قابلة للاسترجاع. ربط مزودي النماذج وحده لا ينفذ هذه القدرات.

من قائمة الملف ذات **32 بنداً**: **14 متحققاً ضمن نطاقنا، 14 جزئياً، و4 غير منفذة**. البنود متفاوتة الجهد، لذلك هذه أعداد تصنيف وليست نسبة إنجاز للمشروع. عبارات 100% في سجل مهام الدفعة السابقة تخص المهام المحددة هناك؛ لا تشمل الرؤية الأوسع لهذا الملف.

## النسخة المقاسة وحدود الأدلة

- أحدث regression: **239 اختباراً**؛ هذه اختبارات برمجية تجمع المسارات الحالية، وليست 239 برنامجاً أو مشاركاً مستقلاً.
- **34 فحص متصفح**: 27 عادياً و7 لحالات فشل/مزود مضبوط، بلا page errors أو طلبات متصفح خارجية.
- تشخيص timeout الجديد يعرض تكرار قيم شرط while وتحديثاً بقيت قيمته ثابتة، مع source/event links. هو وصف لقطات في prefix مسجل، ولا يثبت حلقة لا نهائية أو السبب الجذري لكل برنامج.
- زر القياس يحترم الآن use_ai والموديل والموافقة والـcache؛ أقسام AI تشرح disabled/unavailable/abstention عوض عرض أقواس فارغة. لا يضمن هذا جودة فرضيات الموديل.
- تجربة محلية أولى رجعت فرضيتين متعارضتين؛ تجربة لاحقة بعد تعديل السياق والتعليمات رجعت امتناعاً. النتيجتان محفوظتان؛ نجاح النقل والمخطط لا يثبت صحة التفسير.
- تجربة QuixBugs السابقة تخص سبع عائلات عامة مكشوفة؛ إعادة الإنتاج النظيفة السابقة عند `1aee128`، ودراسة السياق عند `2d6d284`. **لم نعد دراسة الدقة الكاملة بعد تغييرات التعليمات في 5f58330**، فلا تُنسب نتائجها للنسخة الجديدة باعتبارها قياساً جديداً.
- [أدلة إصلاح التشخيص](v4-evidence/timeout-diagnosis-20261127/MANIFEST.json) و[أدلة الدفعة السابقة](v4-evidence/completion-20261127/MANIFEST.json).

## 2. التقنيات والخوارزميات المذكورة

| التقنية | الحالة | التفسير |
|---|---|---|
| AST / CFG / Data Flow | جزئي | Python AST موجود؛ CFG وdef-use وcontrol subset فقط، دون heap/alias/calls عامة. |
| Differential / Property-Based | منفّذ محدود | مقارنة بالمرجع وتوليد Hypothesis؛ لا property grammar عامة للمسائل الجديدة. |
| Metamorphic Testing | غير عام في V4 | فحوص invariant خاصة في V3 لا تساوي محرك metamorphic عام؛ يضاف بعقود موثوقة لكل تحويل. |

| Delta Debugging / Shrinking | جزئي | تصغير قيم وبنية؛ لا ddmin ولا ثبوت local minimum؛ Hypothesis يعمل بمرحلة generate هنا. |

| Mutation Testing / Repair | جزئي | طفرات وأمثلة benchmark وفحص تصحيح موجودة؛ لا mutation framework عام يقيّم كفاية الاختبارات. |

| Training LLM / RL | غير مطلوب الآن | لا يوجد تدريب خاص؛ الملف نفسه لا يطلبه للنسخة الأولى. |

### هل ACDR موجودة؟

لا. المعادلة الواردة في الملف مقترح ترتيب؛ لا يوجد حالياً pool اختبارات وتحديث أوزان/أولوية وتغذية راجعة واستكشاف يحققها.

| الإشارة | الجاهزية | العمل المطلوب |
|---|---|---|
| R — ارتباط الاختبار بالموضع | جزئي | ترتيب أسطر موجود بعد الشاهد؛ تقدير ارتباط اختبار لم ينفذ بعد غير موجود. |
| C — تغطية إضافية متوقعة | جزئي | نقيس بعض التغطية بعد التنفيذ؛ لا مقدّر novelty ولا تغذية راجعة لتوليد الاختبار التالي. |
| B — أهمية الحدود | متاح كبداية | حدود الحقول والبنية موجودة في manifest ويمكن اشتقاق إشارات منها. |
| H — اختبار فرضية | جزئي | proposals مع prediction/hypothesis_index؛ لا مقارنة منهجية بين تفسيرات متنافسة. |
| K — كلفة متوقعة | جزئي | وقت فعلي للطلب والتنفيذ موجود؛ كلفة الحاوية والتتبع منفصلة عن كلفة الخوارزمية، ولا مقدّر قبل التنفيذ. |


الإضافة معقولة كمشروع تالٍ بعد ضبط الأساس: سياسة deterministic بميزانية واستكشاف وسجل قرارات، ثم مقارنة مع Random/Boundary تحت نفس سقف التنفيذ. تضبط الأوزان على بيانات تطوير منفصلة، وتُحفظ جميع حالات الامتناع والفشل. اسم ACDR ليس دليلاً على جدة بحثية أو تفوق؛ يحتاج مراجعة أعمال قريبة وتجربة مستقلة.

## 6. المكتبات: نحتفظ بماذا ونضيف ماذا؟

قائمة الملف مجموعة خيارات، وليست لائحة تثبيت إلزامية. التصنيف يتناول التكامل في المشروع، لا الحزم العالمية على جهاز التطوير.

| الأدوات المذكورة | الوضع الحالي | القرار المقترح |
|---|---|---|
| Python AST / Tree-sitter / ANTLR / JavaParser / Clang LibTooling | Python ast مستخدم. | نستمر به للغة الحالية؛ Tree-sitter للمحرر/لغات أخرى لاحقاً، وأدوات Java/C++ مع اختيار اللغة الثانية. |
| Hypothesis / jqwik / RapidCheck | Hypothesis مدمج. | توسيع استخدامه الحالي قبل jqwik/Java أو RapidCheck/C++. |
| مولدات مخصصة / LibFuzzer | مولدات grammar موجودة. | coverage-guided لاحقاً؛ LibFuzzer ليس مطلباً لتشغيل Python الحالي. |
| Z3 / KLEE | لا تكامل. | توسعة بحثية متقدمة وليست استبدالاً للمرجع والاختبارات. |
| Docker / Isolate / Judge0 / gVisor | Docker worker موجود. | تقييم عزل إضافي أو خدمة تنفيذ قبل النشر العام؛ لا حاجة لتركيبها جميعاً. |
| CPython / GCC / Clang / JDK | مسار التنفيذ CPython. | Java/C++ يحتاجان compiler/runtime وعامل tracing وsource mapping مستقلين. |

Tree-sitter parser متزايد للشجرة النحوية، وليس محرك تحقق خوارزمي. ## 9. فجوات عملية يجب إصلاحها قبل توسيع الادعاءات

1. **توافق قراءة stdin الثنائية:** العامل يضع `io.StringIO` في `sys.stdin`. جربت `sys.stdin.buffer.read()` داخل الحاوية؛ النتيجة `exception / AttributeError` مع تنظيف ناجح. هذه فجوة بالمشغل، لا دليل أن حل المستخدم غلط. القراءة النصية تعمل. [مرجع Python 3.12 عن io](https://docs.python.org/3.12/library/io.html) يفرّق بين StringIO وواجهات التدفق الثنائية.
2. **التصغير وتوقيع الخطأ:** `analyze_package` يقبل أول مرشح من نفس kind ثم يخرج. `exception` قد ينتقل إلى نوع استثناء آخر؛ مطلوب توقيع يطابق الفشل المقصود ومعيار توقف وميزانية معلنة.
3. **حزمة دليل واحدة:** witness يعيد المدخل والمصدر، لكن seed ونسخ الأدوات والطلب والميزانية ليست موحّدة في كل export للتحليل الفردي.
4. **فصل المهلة عن الحكم الخوارزمي:** مهلة sandbox أثناء instrumentation ليست زمن Codeforces؛ profile timeout لا يساوي شاهد خطأ منطقي ولا سبباً مثبتاً.
5. **الإصلاح عند timeout:** `verify_repair` يشترط exception أو wrong answer لإعادة إثبات الشاهد الأصلي، فلا يعالج timeout كمسار إصلاح كامل حالياً.
6. **سياسات المخرجات:** exact/tokens/unordered/float لا تكفي للمسائل الإنشائية متعددة الحلول؛ نحتاج checkers معزولة أو subset مدروس.
7. **رحلة المستخدم:** اختيار package خاطئة أدى إلى Wrong case fields. من المفيد عرض اسم الحزمة والحقول المتوقعة قرب المدخل، وإظهار رسائل عربية ومراجعة مبسطة؛ لا ضرورة لإجبار المستخدم على JSON كبير في المنتج النهائي.
8. **حدود الذكاء:** وجود event ID لا يثبت صحة النص الحر. نتائج النموذج في تجربة timeout الأخيرة تدعم إبقاء فحص القيم مستقلاً وتوضيح الامتناع بدلاً من اختراع تفسير.

| E — ACDR | ranking + exploration + تحديث بعد الدفعات | متوسط/بحثي | مقارنة متساوية الميزانية مع Random/Boundary ومجموعة تقييم منفصلة |
| F — التقييم | حلول مستقلة ووسوم ومراجعة بشرية وablation حقيقية | يعتمد على البيانات والمشاركين | فصل corpus والتطوير والاختبار، وإظهار الإخفاقات والحدود |
| G — قاعدة المعرفة | schema للخطأ والأدلة والصلاحيات والاحتفاظ ثم retrieval | متوسط إلى كبير | إذن استخدام ونسخ وأثر حذف وتقييم استرجاع قبل embeddings |
| H — توسعة المنتج | لغة ثانية، محرر أفضل، scaling/memory benchmarks ونشر عام | كبير | عقود واضحة لكل لغة، tracing موحد، threat review قبل خدمة أكواد عامة |

A–E توصيات تنفيذ، وليست مهام نُفذت خلال هذه المقارنة. ترتيبها لا يفرض إطاراً أو قاعدة بيانات جديدة.

## 11. ما لا أنصح بإضافته الآن وما لا يجوز وعد المستخدم به

- لا أوصي بتغيير backend من Python إلى Spring لمجرد معرفة Java، أو استبدال المكتبات العاملة دون حاجة مثبتة.
- لا أوصي بإضافة LangGraph وLiteLLM وRedis وPostgreSQL وpgvector وMinIO دفعة واحدة.
- لا أوصي بتدريب LLM أو RL أو البدء بـZ3/KLEE قبل إثبات baseline متكيف أبسط.
- دعم Java/C++ ممكن، لكنه ليس تحويل Java إلى Python في الواجهة؛ له compiler/tracing/source mapping وعزل وفحوص منفصلة.
- لا يجوز الوعد بتحديد سبب كل برنامج، أو صحة إصلاح لكل المدخلات، أو Big-O من توقيت مدخل واحد.
- لا يجوز مساواة مصدرين مختلفين باستقلال مرجعين، أو عرض corpus مكشوف كتقييم مستقل، أو ادعاء جدة ACDR دون بحث.
- النشر العام للكود العدائي ينتظر تدقيقاً مستقلاً؛ 14 probes محلياً لا تمنح شهادة أمنية.

## 12. كيف نستخدم نسب الاستثمار الموجودة في الملف؟

45% Core و20% Agent و20% تقييم و10% UI و5% Providers هي **توزيع جهد مقترح**، وليست نسب إنجاز. تتفق المراجعة مع تقليل الاستثمار الإضافي في adapters والتركيز على قوة الشاهد والقرار والتقييم. لا أشتق نسبة عامة من عدّ ملفات أو اختبارات أو بنود متفاوتة الجهد.
